## 0. この文書の目的

本作は、複数の環を回し、発光部品と遮断部品の位置関係を変え、外周の必要な受信点をすべて点灯させるパズルである。初級2問、中級2問、上級1問の合計5問を連続して解き、5問の実プレイ時間の合計を競う。問題は、公開前に検証済みの初級30問・中級30問・上級30問から、挑戦開始時に抽選する。

この文書は、次の目的で使う。

1. ゲームの規則、画面、問題生成、計測、ランキングの解釈を一つに固定する。
2. ChatGPT Workが独自判断で仕様を変えず、6件のPRへ分けて実装できる状態にする。
3. 問題を後から大量に追加しても、解けない問題、重複問題、難度の崩れを混ぜない。
4. 既存作品の固有表現を使わず、独自の石板世界として公開する。
5. iPhone Safariで、説明を読まなくても基本操作を理解できる画面にする。

### 0.1 仕様の優先順位

齟齬が生じた場合は、次の順で判断する。

1. この実装計画書の「固定仕様」
2. `docs/spec/GAME_RULES.md`
3. `docs/spec/PUZZLE_FORMAT.md`
4. 自動テストの期待値
5. 画面デザイン資料
6. 実装上の都合

画面資料とゲーム規則が衝突した場合は、規則を守ったうえで画面を簡略化する。実装上の都合を理由に規則を変えてはならない。

### 0.2 ChatGPT Workの権限

ChatGPT Workは、作業用ブランチの作成、実装、テスト、コミット、Draft PRまたは通常PRの作成まで進めてよい。

次は禁止する。

- `main`への直接push
- PRのマージ
- 履歴の強制書き換え
- ユーザーの許可がない依存関係の大規模更新
- 別ゲームや実験場の無関係な修正
- 秘密鍵、Service Role Key、個人情報のコミット
- 既存作品の画像、音、文章、問題配置、固有名称の持ち込み

各PRは、直前のPRがマージされた最新の`main`から作る。未マージのPRを土台に次のPRを重ねない。

## 4. ゲーム規則

### 4.1 盤面の座標

公開版は、円周を12区画に分ける。区画番号は上を`0`として、時計回りに`0`から`11`までとする。

可動環は3本で、内側から次の順に固定する。

- `ringIndex: 0` = 内側の環
- `ringIndex: 1` = 中央の環
- `ringIndex: 2` = 外側の環

外周の受信点は回転しない。

各環は、現在の回転量を`0`から`11`の整数で持つ。部品の実際の区画は次で求める。

```text
worldSlot = (localSlot + rotation + 12) % 12
```

負の値をそのまま使わず、必ず`0`から`11`へ正規化する。

### 4.2 部品

初期公開で使う部品は3種類だけにする。

| 部品 | 見た目 | 働き |
|---|---|---|
| 発光紋 | 赤橙色の太陽形 | 有効時に中心方向へ光を出す |
| 遮断石 | 黒灰色のX形 | ぶつかった光を止める |
| 受光紋 | 外周の緑色の二重円 | 必須受信点。光が届くと点灯する |

色だけで区別させない。形、線、表示名でも区別できるようにする。

1本の環の同じ`localSlot`へ、複数の部品を置いてはならない。

### 4.3 発光の切替

発光の有効・停止は、環単位で持つ。

```text
emissionEnabled[ringIndex]: boolean
```

選択中の環で「光を止める」または「光を出す」を押すと、その環にあるすべての発光紋の状態が切り替わる。

停止中の発光紋は光を出さない。ただし、石の部品として盤面に残り、他の発光紋から来た光を遮る。

### 4.4 光の進み方

有効な発光紋ごとに、次の順で判定する。

1. 発光紋がある環から、同じ区画を中心へ向かう。
2. 発射元より内側にある環を、外側から内側の順で調べる。
3. 遮断石または別の発光紋が同じ区画にあれば、その位置で止める。
4. 中心まで届いた場合は、反対側の区画へ進む。
5. 反対側は次で求める。

```text
oppositeSlot = (sourceWorldSlot + 6) % 12
```

6. 中心から外側へ、内側の環から外側の環の順で調べる。
7. 遮断石または発射元以外の発光紋が反対側の区画にあれば、その位置で止める。
8. 外周まで届き、その区画が必須受信点なら点灯させる。
9. 複数の光が同じ受信点へ届いても、点灯は1件として数える。
10. 光どうしは中央や途中で交差しても、互いを遮らない。

発射元自身は、自分の光を遮らない。別の環または同じ環の反対側にある発光紋は遮断物として扱う。

### 4.5 成功条件

必須受信点の集合を`targetMask`、現在点灯している受信点の集合を`litMask`とする。

```text
(litMask & targetMask) === targetMask
```

上の条件を満たした瞬間に、その問題を解いたものとする。

必須でない方向へ光が抜けていても失敗にしない。すべての光を外周へ通す必要もない。

### 4.6 操作と手数

| 操作 | 状態変更 | 手数 |
|---|---:|---:|
| 環を選ぶ | 選択状態だけ変更 | 0 |
| 左へ1区画回す | 回転量を-1 | 1 |
| 右へ1区画回す | 回転量を+1 | 1 |
| 発光を出す・止める | 選択環の状態を反転 | 1 |
| 遊び方を開く | なし | 0 |
| 音を切り替える | なし | 0 |

競技中に「1手戻す」は置かない。反対へ回せば元へ戻せるが、その操作も1手として数える。

競技中に現在の問題だけを初期化するボタンは置かない。誤操作も含めてタイムと手数を競う。中断する場合は、確認後に1回の挑戦全体を終了する。

練習では「最初からやり直す」を使える。練習の記録はランキングへ送らない。

### 4.7 入力の反映

入力を受けた時点で内部状態を即時に確定し、成功判定と時間停止を行う。回転アニメーションの終了を待たない。

表示上の回転は120ミリ秒を標準とするが、連続入力を妨げない。アニメーション中も次の操作を受け付け、内部の整数状態を基準に表示を追従させる。

端末の描画速度をゲームの計測へ混ぜない。

## 5. 5問チャレンジの流れ

### 5.1 画面状態

画面の状態は、文字列の寄せ集めではなく、次の状態として型で管理する。

```text
boot
home
howToPlay
modeSelect
preparingRun
countdown
playing
stageSolved
runResult
leaderboard
submissionPending
fatalError
```

`playing`には、問題番号、問題ID、問題庫の版、開始状態、現在状態、問題タイム、手数を持たせる。

### 5.2 ホーム

ホームには、次だけを主要情報として置く。

- 正式なゲーム名
- 「5つの石板を解き、合計時間を競います」
- 「初級2問・中級2問・上級1問を出題します」
- 名前入力
- 「5問チャレンジ」
- 「練習」
- 「遊び方」
- ホーム用シェア
- カメレオンJPの実験場へのリンク
- 音の設定

名前欄の例文は「名前を入力してください」とする。特定の人名を例にしない。

名前は前後の空白を除き、1〜16文字にする。改行、制御文字だけの名前、空白だけの名前は拒否する。表示名だけで端末を識別せず、送信制限と未完了挑戦の照合には端末内で作ったランダム識別子を別に使う。

### 5.3 問題の抽選

競技用の抽選はブラウザで行わない。開始ボタンを押した後、サーバーへ`prepare`を送り、次の条件を満たす5問を受け取る。

1. 有効な問題庫の版から選ぶ。
2. 初級2問、中級2問、上級1問とする。
3. 同じ挑戦内で同じ問題を重複させない。
4. 表示順は、初級、初級、中級、中級、上級で固定する。
5. 抽選した問題ID、問題内容のチェックサム、順序を`runToken`へ固定する。
6. 既に未完了の`prepared`または`active`な挑戦がある端末には、新しい組合せを発行せず、同じ5問を返す。
7. 問題庫の版が変わっても、開始済みの挑戦は開始時の版で最後まで検証する。

問題の抽選には、サーバー側の安全な乱数を使う。クライアントの`Math.random()`、端末時刻、表示名、URLの値だけで抽選結果を決めない。

### 5.4 競技開始

抽選された5問すべてのデータ、チェックサム、必要な画面部品を読み込み、形式検査を終えてから3秒のカウントダウンを始める。

問題の抽選中、取得中、検査中にタイムを開始してはならない。

カウントダウン終了後、盤面と操作ボタンが入力可能になった同じ処理内で、第1問の時間を開始する。

### 5.5 問題間の遷移

問題を解いた瞬間に、その問題の時間を止める。

次に、次の情報を900ミリ秒から1,200ミリ秒の範囲で表示する。

- 「石板を解きました」
- 問題タイム
- 手数
- 次の問題番号と難度

この遷移時間は合計へ含めない。

次の盤面を表示し、入力可能にした時点で次の問題時間を開始する。CSSアニメーションの完了イベントを時間開始の基準にしない。

### 5.6 結果

第5問を解いたら、次を表示する。

- 5問の合計時間
- 第1問から第5問までの個別時間
- 問題ごとの難度
- 問題ごとの手数
- 総手数
- 問題庫の版
- 送信状態
- 順位
- 上位10件
- もう一度
- 練習する
- 結果をシェア
- カメレオンJPの実験場へ戻る

ランキング送信に失敗しても、結果画面を消さない。「再送する」を常に押せるようにする。

### 5.7 競技と練習

#### 5問チャレンジ

- サーバーが初級2問・中級2問・上級1問を抽選する。
- 抽選した5問は、その挑戦の`runToken`へ固定する。
- ランキングへ送信する。
- 途中で再読込した場合は挑戦を無効にする。
- 遊び方を開いても時間は止めない。
- 問題のやり直しはできない。
- 中断して開始画面へ戻っても、未完了挑戦の有効期限内は同じ5問を返し、引き直しを防ぐ。

#### 練習

- 初級30問・中級30問・上級30問から、初級2問・中級2問・上級1問を選ぶ。
- 同じ1回の練習内で重複させない。
- ランキングへ送信しない。
- 問題を最初からやり直せる。
- 遊び方を開いている間は、練習タイムを止めてもよい。
- 最後に参考タイムとして表示する。

### 5.8 公平性の扱い

難度の内訳を全員で同じにしても、別の問題を引く以上、全員が数学的に完全な同一条件になるわけではない。この点を隠さない。

本作では、次の方法で問題差を小さくし、実用上の公平性を保つ。

1. 90問すべてを同じ規則版で作り、全解法検査を通す。
2. 各問題へ、最短手数、最短解数、必要な発光切替、分岐数、推定解答時間から校正値を付ける。
3. 初級と中級は、2問の校正値合計が基準範囲に入る組合せだけを抽選候補にする。
4. 上級30問は、1問ごとの校正値を狭い範囲へそろえる。
5. 抽選候補を「抽選券」として事前生成し、各問題が抽選券へ同じ回数だけ現れるようにする。
6. 初期問題庫では抽選券を900件作る。初級と中級の各問題は60件、上級の各問題は30件の抽選券へ含める。
7. サーバーは抽選券を均等確率で1件選ぶ。
8. 未完了挑戦では別の抽選券へ変更しない。
9. 問題庫を差し替えた場合は`poolVersion`を上げ、旧版と新版のランキングを混ぜない。

ランキング値は補正後の点数ではなく、5問の実測合計時間を使う。校正が基準を満たせない問題は問題庫へ入れない。公開後の実測で特定問題だけ明らかに速い、または遅いことが分かった場合は、記録を後から書き換えず、その問題を除いた新しい問題庫の版を作る。

## 6. 時間計測と順位

### 6.1 保存単位

時間は整数のミリ秒で保存する。画面では100分の1秒まで表示する。

```text
displaySeconds = floor(timeMs / 10) / 100
```

内部値を表示用に丸めてから合計してはならない。合計は未丸めの整数値を足す。

```text
totalTimeMs =
  stage1TimeMs
  + stage2TimeMs
  + stage3TimeMs
  + stage4TimeMs
  + stage5TimeMs
```

### 6.2 計測開始と停止

各問題について、次を守る。

- 開始: 盤面が表示され、操作受付を有効にした時点
- 停止: 状態変更後の成功判定が真になった時点
- 除外: 問題抽選、読み込み、形式検査、カウントダウン、4回の問題間演出、結果演出
- 含む: 考えている時間、遊び方を開いた時間、画面を一時的に離れた時間

### 6.3 画面が背面へ移った場合

競技中にブラウザが背面へ移った場合、時間を止めない。

実装は次の二つを記録する。

- 画面内の細かな経過を測る単調増加時計
- 背面時間を補う端末時刻

画面が再表示されたときは、両方の差を比較し、短くなる側を採用しない。端末時刻が逆戻りした場合、または不自然に大きく変わった場合は、その挑戦をランキング対象外として結果だけ表示する。

画面の回転では挑戦を失効させず、状態と時間を維持する。

### 6.4 再読込と終了

競技中の再読込、タブ終了、ブラウザ終了では、競技を再開しない。未完了の競技状態を検出した場合は、ホームで「前回の挑戦は中断されました」と表示する。

サーバー側の未完了割当はすぐ削除しない。同じ端末が有効期限内に再度開始した場合は、引き直し防止のため同じ5問を返す。

練習は、現在の問題と状態を端末内へ保存し、同じ端末で1回だけ再開できるようにしてよい。

### 6.5 順位

順位の比較順は固定する。

1. `total_time_ms`が小さい
2. `total_moves`が小さい
3. `validated_at`が早い

名前の文字列順、抽選順、端末性能は順位に使わない。

同じ問題庫の版だけを同じランキングへ載せる。問題庫の版が変わった場合は、新しいランキングとして開始する。

同じランキング上の名前の扱いは、カメレオンJPの実験場で使用中の共通ルールに合わせる。端末識別子はランキング名の代わりに使わず、引き直し防止、二重送信防止、送信制限だけに使う。

## 7. 問題データ

### 7.1 公開用問題形式

問題はコードへ直書きせず、版を持つJSONとして保存する。

```json
{
  "schemaVersion": 1,
  "rulesetVersion": "stone-rings-v1",
  "generatorVersion": "generator-v1",
  "id": "sr1-easy-000001",
  "difficulty": "easy",
  "slotCount": 12,
  "rings": [
    {
      "id": "inner",
      "parts": [
        { "kind": "emitter", "slot": 1 },
        { "kind": "blocker", "slot": 7 }
      ]
    },
    {
      "id": "middle",
      "parts": [
        { "kind": "emitter", "slot": 4 },
        { "kind": "blocker", "slot": 9 }
      ]
    },
    {
      "id": "outer",
      "parts": [
        { "kind": "emitter", "slot": 8 },
        { "kind": "blocker", "slot": 2 }
      ]
    }
  ],
  "targets": [0, 3, 6, 9],
  "initialState": {
    "rotations": [2, 5, 8],
    "emissionEnabled": [true, true, true]
  },
  "contentChecksum": "sha256:REPLACED_BY_GENERATOR"
}
```

例の配置を本番問題として使ってはならない。

### 7.2 検証用情報

公開用定義とは別に、生成・検査時だけ使う情報を持つ。

```json
{
  "puzzleId": "sr1-easy-000001",
  "canonicalSignature": "sha256:...",
  "shortestMoves": 5,
  "shortestSolutionCount": 2,
  "requiredRingIndexes": [0, 2],
  "requiredToggleCount": 0,
  "visitedStateCount": 624,
  "calibrationScore": 1000,
  "estimatedSolveTimeMs": 8000,
  "validatedWithRuleset": "stone-rings-v1",
  "validatedWithSolver": "solver-v1"
}
```

正解操作列は公開画面へ送らない。リポジトリへ保存する場合も、通常の問題JSONとは分離する。

### 7.3 問題庫

公開前に、次の90問を固定する。

- 初級30問
- 中級30問
- 上級30問

問題庫は`poolVersion`を持つ。日付や曜日では切り替えない。

```json
{
  "schemaVersion": 1,
  "poolVersion": "pool-v1",
  "rulesetVersion": "stone-rings-v1",
  "generatorVersion": "generator-v1",
  "puzzleIdsByDifficulty": {
    "easy": ["sr1-easy-000001", "...29件省略..."],
    "normal": ["sr1-normal-000001", "...29件省略..."],
    "hard": ["sr1-hard-000001", "...29件省略..."]
  },
  "drawProfile": {
    "order": ["easy", "easy", "normal", "normal", "hard"],
    "ticketCount": 900,
    "easyAppearancesPerPuzzle": 60,
    "normalAppearancesPerPuzzle": 60,
    "hardAppearancesPerPuzzle": 30
  },
  "drawTicketsChecksum": "sha256:REPLACED_BY_GENERATOR",
  "poolChecksum": "sha256:REPLACED_BY_GENERATOR"
}
```

抽選券の実データはサーバー側の非公開領域に保存する。各抽選券は、初級2問、中級2問、上級1問の5問IDを持つ。

一度ランキングを受け付けた問題庫は上書きしない。問題に欠陥が見つかった場合は、旧版の受付を止め、新しい`poolVersion`を作る。既存の記録が参照する問題JSON、抽選券、チェックサムを変更しない。

### 7.4 入力検査

問題JSONを読み込むときは、実行時の形式検査を必ず行う。次を拒否する。

- `slotCount`が12でない
- 環が3本でない
- 区画が0〜11の外
- 同じ環の同じ区画に複数部品がある
- 発光紋が0個
- 必須受信点が0個
- 必須受信点が重複
- 初期回転量が0〜11の外
- 発光状態の数と環の数が違う
- 未対応の`rulesetVersion`
- チェックサム不一致

壊れた問題はプレイ開始前に止め、別問題へ黙って差し替えない。抽選された5問のどれかが不正なら「現在の問題を開始できません」と表示し、その`runToken`を開始状態へ移さない。

## 8. 全解法検査

### 8.1 最短解を確認する方法

開始状態に近い状態から順に、すべての操作を広げて調べる。この方法を幅優先探索（Breadth-First Search）と呼ぶ。

選択中の環は解法状態へ含めない。環の選択は手数ではないため、解法上は任意の環へ直接操作できるものとして扱う。

3環・12方向の場合、論理状態の上限は次となる。

```text
12^3 × 2^3 = 13,824状態
```

状態には、3本の回転量と3本の発光状態だけを含める。

### 8.2 探索操作

各状態から、次の9操作を固定順で調べる。

1. 内側を左回転
2. 内側を右回転
3. 内側の発光切替
4. 中央を左回転
5. 中央を右回転
6. 中央の発光切替
7. 外側を左回転
8. 外側を右回転
9. 外側の発光切替

固定順にすることで、同じ入力から同じ代表解を得られるようにする。

### 8.3 状態の符号化

状態を文字列JSONのまま比較しない。回転量と発光状態を衝突しない整数または固定長文字列へ変換する。

符号化と復号の往復テストを行う。

```text
decode(encode(state)) === state
```

全13,824状態について重複キーがないことをテストする。

### 8.4 探索の結果

探索は、次を返す。

- 解けるか
- 最短手数
- 最短解の件数
- 代表解
- 最短解で操作される環
- 最短解で必要な発光切替数
- 調べた状態数
- 探索が打ち切られたか

最短解の件数は、難度ごとの上限を超えた時点で数えるのを止めてよい。ただし「1件」と「上限超過」を同じ値にしない。

## 9. 問題生成

### 9.1 基本方針

部品を無作為に置いて、そのまま問題として採用してはならない。

次の順で生成する。

1. 難度に応じた部品数を決める。
2. 各環へ発光紋と遮断石を置く。
3. 完成状態となる回転量と発光状態を作る。
4. その状態で外周まで届く光を計算する。
5. 点灯可能な場所から必須受信点を選ぶ。
6. 完成状態へ複数の合法操作を加えて開始候補を作る。
7. 全解法を調べる。
8. 初期状態で未完成か確認する。
9. 最短手数、必要操作、最短解数、見た目の密度が基準内か確認する。
10. 回転・反転しただけの同一問題を除外する。
11. 問題IDとチェックサムを付けて保存する。

問題の採用判断は、作成時の崩し手数ではなく、探索で求めた実際の最短手数を使う。

### 9.2 乱数

競技用の問題生成で`Math.random()`を使わない。

文字列シードを固定した疑似乱数へ変換し、同じ次の値から同じJSONが生成されるようにする。

- シード
- 生成器の版
- 規則の版
- 難度
- 連番

同じシードと版で、別の実行環境でもバイト単位で同じ問題が出ることを固定試験で守る。

乱数方式を変えた場合は、`generatorVersion`を上げる。既存問題を再生成して上書きしない。

### 9.3 初期難度

初期公開は、次の範囲を使う。実機試遊で変更する場合は、生成器の設定版を上げ、既存問題の難度名を書き換えない。

| 条件 | 初級 | 中級 | 上級 |
|---|---:|---:|---:|
| 最短手数 | 4〜6 | 7〜10 | 11〜15 |
| 必須受信点 | 4〜5 | 5〜6 | 6〜7 |
| 発光紋の合計 | 3〜4 | 4〜5 | 5〜6 |
| 遮断石の合計 | 2〜3 | 3〜4 | 4〜5 |
| 最短解で使う環 | 2本以上 | 3本 | 3本 |
| 発光切替 | 不要でもよい | 1回以上必須 | 1回以上必須 |
| 最短解数 | 4件以下 | 3件以下 | 2件以下 |
| 初期状態から1手で成功 | 不可 | 不可 | 不可 |

見た目を複雑にしすぎないため、1本の環に置く部品は4個までにする。

### 9.4 重複の除外

盤面全体を同じ角度だけ回した問題は、別問題として数えない。左右を反転しただけの問題も同一として扱う。

各問題について、全体回転12通りと、その左右反転12通りの合計24通りから、辞書順で最小の表現を`canonicalSignature`とする。

次を禁止する。

- 同じ`canonicalSignature`
- 90問問題庫の中で、必須受信点と全部品配置が同一
- 同じ抽選券の5問の中で、別問題の単純な回転または反転になっている組合せ
- 直前の問題庫の版と90%以上同一なのに、版変更理由が記録されていない更新

似ている問題は、自動削除だけで終わらせず、HTMLレポートへ並べて確認できるようにする。

### 9.5 部品が意味を持つこと

難度を水増しするだけの部品を減らすため、採用前に次を検査する。

- 最短解で指定本数の環が実際に操作される
- 中級・上級では発光切替が実際に必要
- 必須受信点がすべて、少なくとも1本の有効な光で到達可能
- 初期状態で点灯数が必須数と同じではない
- 全受信点が常時点灯するだけの発光紋がない
- 発光紋がすべて停止した状態だけが正解にならない
- どの操作をしても点灯数が変わらない環を採用しない

### 9.6 量産・問題庫・抽選券用コマンド

PR2で、次のコマンド名を用意する。

```bash
npm run puzzles:generate -- --seed pool-v1-candidates --per-tier 300
npm run puzzles:validate -- --input content/candidates
npm run puzzles:report -- --input content/candidates
npm run pool:create -- --version pool-v1 --per-tier 30
npm run pool:validate -- --input content/pools/pool-v1.json
npm run tickets:create -- --pool pool-v1 --count 900
npm run tickets:validate -- --pool pool-v1
npm run selection:simulate -- --pool pool-v1 --runs 100000
```

`puzzles:report`は、各問題の縮小盤面、難度、最短手数、最短解数、必要環、切替回数、校正値、重複判定を1つのHTMLへ出す。iPhoneのブラウザから確認できる構成にする。

`pool:create`は、検証済み候補から初級30問、中級30問、上級30問だけを採用する。不足していても、基準外の問題で埋めない。

`tickets:create`は、初級2問、中級2問、上級1問の900件の抽選券を作る。各問題の出現回数を仕様どおりそろえ、初級2問と中級2問の校正値合計が許容範囲へ入る組合せだけを採用する。

`selection:simulate`は10万回の抽選を再現し、次を確認する。

- 毎回、初級2問・中級2問・上級1問になる
- 1回の抽選内に重複がない
- 各抽選券が均等な確率で選ばれる
- 各問題の出現率が期待値から大きく外れない
- 5問の校正値合計の分布が許容範囲に収まる

通常のPR検査では、各難度30問以上を固定シードで生成して検査する。公開前の手動検査では、各難度300問以上を生成し、90問の採用理由、採用率、失敗理由を記録する。

GitHub Actionsで定期生成しない。問題庫を更新するときだけ、ChatGPT Workまたは手動実行で生成する。

### 9.7 問題を追加・差し替えする運用

問題を追加または差し替える場合も、現在の`poolVersion`を上書きしない。

1. 新しい問題庫の版を決める。
2. 新しいバッチ用シードを決める。
3. 各難度300問以上の候補を生成する。
4. 全解法検査を行う。
5. HTMLレポートで見た目を確認する。
6. 重複、校正値、難度分布を確認する。
7. 初級30問、中級30問、上級30問を採用する。
8. 900件の抽選券を作る。
9. 各問題の出現回数と5問合計の校正分布を検査する。
10. 10万回の抽選試験を行う。
11. 問題JSON、問題庫JSON、抽選券、データ移行だけのPRを作る。
12. 公開後は旧問題庫の記録を残し、新しい問題庫のランキングを別に開始する。

問題庫更新PRでは、規則、UI、光路判定、時間計測を同時に変更しない。

## 10. 画面設計

### 10.1 見た目の方針

石板らしさは、盤面を読みにくくしない範囲に抑える。

使う装飾は次までにする。

- 外枠の石の厚み
- 少数のひび
- 端に限った苔
- 環の浅い彫り
- 部品の独自記号
- 選択環の淡い発光
- 成功時の短い発光

盤面の部品の後ろへ、細かな文字、強い斑点、密なひびを置かない。実在言語に見える装飾文を並べない。

### 10.2 色と形

- 石板: 明るさの違う灰褐色
- 発光紋: 赤橙色、太陽形
- 遮断石: 黒灰色、X形
- 必須受信点: 緑色、二重円
- 選択中の環: 青緑色の輪郭と太い線
- 通過中の光: 赤橙色から淡い白
- 遮断地点: 短い火花または小さな衝突印

色覚だけに依存しない。モノクロ表示でも、発光紋、遮断石、受信点を形で見分けられることを画像試験で確認する。

### 10.3 縦画面

幅320〜430ピクセルでは、次の順に置く。

1. ヘッダー
2. 問題番号、タイム、点灯数
3. 円形盤面
4. 選択中の環
5. 左回転、発光切替、右回転
6. 中断、遊び方
7. 必要時だけ表示する短い状態文

盤面は、幅の92%以内かつ高さを圧迫しない正方形にする。左右の常設説明欄は置かない。

操作部は画面下部へ固定してよいが、盤面や結果を隠してはならない。iPhoneの下端の安全領域を加える。

### 10.4 横画面とPC

横画面では、左に盤面、右に情報と操作を置いてよい。縦画面と操作順を変えない。

PCでは、次のキーに対応する。

- `1`, `2`, `3`: 内側、中央、外側を選択
- 左矢印: 左回転
- 右矢印: 右回転
- `Space`: 発光切替
- `Escape`: 中断確認を閉じる

キーボード操作を追加しても、画面上のボタンを省かない。

### 10.5 タップ領域

主要ボタンは、縦横48ピクセル以上を確保する。環をタップする領域は、見えている細い線だけにせず、透明な太い当たり領域を重ねる。

盤面内では、次を防ぐ。

- 文字選択
- 画像保存メニュー
- ダブルタップによる誤拡大
- 盤面を操作したときのページスクロール

ページ全体の通常スクロールや、説明文の選択まで一律に禁止しない。

### 10.6 表示情報

プレイ中に常時表示する情報は、次の4点に絞る。

- 問題 1/5
- タイム
- 点灯 4/6
- 選択中の環

手数は小さく表示してよいが、タイムや点灯数より目立たせない。

部品一覧、長い説明、問題生成情報はプレイ中の常設表示にしない。

### 10.7 操作の説明

初回説明は、次の順で見せる。

1. 環を選ぶ
2. 左右へ回す
3. 赤い発光紋から出た光が中心を通る
4. 黒い遮断石と別の発光紋に当たると止まる
5. 外周の緑の受光紋をすべて点灯させる
6. 第3問以降の中級・上級では、環の光を出す・止める操作が必要になる

長文を1画面へ詰め込まず、図と短文で3枚以内に分ける。

### 10.8 成功演出

成功判定後に入力を止め、次を行う。

- 受信点を1回だけ明るくする
- 石板中央の紋を短く点灯する
- 「石板を解きました」を表示する
- 個別タイムと手数を表示する

演出は700ミリ秒以内を目安にし、時間停止後に行う。大量の粒子、画面揺れ、長い白画面を使わない。

### 10.9 音

外部の効果音素材を前提にしない。短いクリック音、遮断音、成功音は、独自に作るか、Web Audio APIで合成する。

初回の自動再生はしない。利用者が最初に画面を操作した後だけ鳴らす。

音がなくても状態が分かるようにする。

## 11. 利用しやすさ

### 11.1 読み上げ

- 盤面全体に、現在の問題と点灯数を説明する名前を付ける。
- 各環の選択ボタンへ「内側の環を選択」のような名前を付ける。
- 選択中の環は`aria-pressed`または同等の状態で伝える。
- 回転ボタンは「選択中の環を左へ1区画回す」とする。
- 発光切替は現在状態に応じて「中央の環の光を止める」などへ変える。
- 点灯数は操作後に通知する。
- タイマーを毎秒読み上げない。
- 成功、送信成功、送信失敗は通知する。

### 11.2 動きを減らす設定

端末が動きを減らす設定の場合は、次を無効または短縮する。

- 環の回転補間
- 発光の脈動
- 成功時の拡大
- 背景の動き

内部状態と時間の扱いは変えない。

### 11.3 文字拡大

ブラウザの文字を200%へ拡大しても、名前入力、開始ボタン、操作ボタン、中断確認、結果の主要情報が隠れないようにする。

説明文はスクロールしてよい。盤面を極端に縮小して、操作不能にしてはならない。

## 13. ランキングとSupabase

### 13.1 基本方針

クライアントからランキング表へ直接`insert`または`update`しない。

競技の開始、抽選、開始確定、中断、完了は、専用のSupabase Edge Functionへ送る。Edge Functionが問題を抽選し、操作履歴を同じ規則コードで再生し、有効な結果だけを共通ランキング表へ保存する。

クライアントにはPublishable Keyだけを置く。Service Role Keyは、Supabase側の秘密としてのみ扱い、GitHub、公開JavaScript、ログ、画面へ出さない。

### 13.2 カメレオンJP共通表への登録

`public.games`には、次の値で登録する。正式名と識別子は確定後に置き換える。

```text
game_slug = <GAME_SLUG>
score_order = asc
score_unit = 秒
score_scale = 1000
score_decimals = 3
score_label = 5問合計タイム
first_score_label = 初回タイム
best_score_label = ベストタイム
top_ranking_type = best
submission_mode = verified
is_active = false  # PR6の公開確認完了までfalse
```

有効な記録は、既存の`public.score_runs`と`public.game_scores`を共通の記録元として使う。`score`には5問の合計ミリ秒を整数で保存する。

`score_runs.metadata`には、少なくとも次を保存する。

- 検証済み記録であること
- `pool_version`
- 5つの問題ID
- 5つの問題チェックサム
- 5問の個別時間
- 5問の個別手数
- 総手数
- 操作履歴の件数とハッシュ
- `run_token`
- クライアント版
- 規則版

タイムが同じ場合に総手数を比較するため、専用のランキング取得関数`get_<GAME_SLUG>_ranking_v1`を作る。

### 13.4 読み取り範囲

一般閲覧では、次だけを読めるようにする。

- 有効な問題庫の版
- 問題庫が初級30問・中級30問・上級30問であること
- 上位10件の表示名
- 5問の合計時間
- 総手数
- 順位
- 記録時刻

90問全部と抽選券の実データは、通常の一覧取得で一括配信しない。競技では、`runToken`へ割り当てた5問だけをEdge Functionから返す。

次を一般閲覧へ出さない。

- 端末識別子
- 接続元のハッシュ
- 操作履歴
- 抽選券一覧
- 検証失敗理由の内部詳細
- サーバー秘密値
- 非公開または停止済み問題庫

行単位の閲覧・書込制御を有効にし、匿名クライアントの直接書込を拒否する。

### 13.5 Edge Functionの操作

同じ入口で、次の`action`を扱う。

- `prepare`: 有効な問題庫と抽選券を選び、5問を`runToken`へ固定して返す
- `begin`: 5問の読み込み完了後に開始状態へ移す
- `abandon`: 中断を記録する。引き直し防止期間中は割当を保持する
- `finish`: 5問の操作履歴を再生し、結果を検証して保存する

同じ端末に未完了の挑戦がある場合、`prepare`は新しい抽選券を発行せず、同じ`runToken`と5問を返す。

### 13.6 送信内容

操作履歴は本文を小さくするため、長いキー名を各操作へ繰り返さず、型で定義した固定長配列を使ってよい。

```json
{
  "schemaVersion": 1,
  "runToken": "SERVER_ISSUED_UUID",
  "poolVersion": "pool-v1",
  "clientInstanceId": "LOCAL_RANDOM_UUID",
  "displayName": "プレイヤー名",
  "stages": [
    {
      "puzzleId": "sr1-easy-000101",
      "puzzleChecksum": "sha256:...",
      "timeMs": 5321,
      "moveCount": 7,
      "actions": [
        [1, 410, "r", 0, 1],
        [2, 920, "t", 1, 0]
      ]
    },
    { "puzzleId": "sr1-easy-000022", "puzzleChecksum": "sha256:...", "timeMs": 6100, "moveCount": 8, "actions": [] },
    { "puzzleId": "sr1-normal-000084", "puzzleChecksum": "sha256:...", "timeMs": 8800, "moveCount": 10, "actions": [] },
    { "puzzleId": "sr1-normal-000013", "puzzleChecksum": "sha256:...", "timeMs": 9100, "moveCount": 11, "actions": [] },
    { "puzzleId": "sr1-hard-000039", "puzzleChecksum": "sha256:...", "timeMs": 14200, "moveCount": 15, "actions": [] }
  ],
  "totalTimeMs": 43521,
  "totalMoves": 51,
  "clientBuild": "GIT_COMMIT_SHA"
}
```

上の空配列は形式説明を短くするための省略であり、実送信では各問題の完全な操作履歴を入れる。

絶対時刻を操作履歴の基準にせず、各問題開始からの経過ミリ秒を使う。

### 13.7 サーバー検証

Edge Functionは、次の順で検査する。

1. 送信JSONの大きさと形式
2. 名前の長さと禁止制御文字
3. `runToken`が存在し、`active`で、有効期限内か
4. `poolVersion`が開始時の割当と一致するか
5. 5つの問題ID、難度順、問題チェックサムが割当と一致するか
6. 初級2問・中級2問・上級1問で、重複がないか
7. 規則の版が対応しているか
8. 操作番号が1から連続しているか
9. 操作時刻が負でなく、前の操作より小さくないか
10. 各操作が許可された種類か
11. 送信された手数と、状態変更操作数が一致するか
12. 各問題を開始状態から再生できるか
13. 5問すべての最終状態が成功条件を満たすか
14. 各問題タイムが最後の操作時刻以上か
15. 合計時間が5問の合計と一致するか
16. 総手数が5問の合計と一致するか
17. 1問題300手以下、合計15分以下か
18. サーバー側の開始・完了時刻と比べ、不自然に短い報告でないか
19. 送信頻度の上限を超えていないか
20. 同じ`runToken`の完了済み結果と内容が一致するか
21. 同じ名前の既存記録より良いか、同タイムなら総手数が少ないか

不正または壊れた送信は、具体的な内部判定をクライアントへ返しすぎない。利用者向けには「記録を確認できませんでした」とし、サーバーログには検証コードを残す。

### 13.8 再送

通信失敗時は、送信内容を端末内へ1件だけ保存する。

- 結果画面に「未送信」と表示
- 「再送する」を表示
- 同じ`runToken`と同じ結果の二重送信は同じ成功結果を返す
- 次回起動時に未送信があれば知らせる
- 自動連打しない
- 送信成功後に端末内の未送信データを削除
- 検証不合格は通信失敗として無限再送しない

### 13.9 送信制限

初期値として、次を設ける。

- 同じ端末識別子: 5分で10回まで
- 同じ接続元: 1時間で60回まで
- 送信本文: 128キロバイト以下
- 1問題: 300操作以下
- 1挑戦: 1,500操作以下
- 1挑戦: 15分以下
- 未完了割当の保持: 30分

上限を超えた挑戦はローカル結果として表示できるが、ランキングには登録しない。

## 14. エラーと復旧

### 14.1 起動失敗

初期データの取得に失敗した場合は、白画面にしない。

表示する内容:

- 「ゲームを読み込めませんでした」
- 「再試行」
- カメレオンJPの実験場へのリンク
- 短いエラー識別番号

再試行ではページ全体を再読込せず、失敗した取得だけをやり直す。

### 14.2 問題取得失敗

競技開始前なら、タイムを始めずに再試行する。

競技途中で次問題の取得に失敗しないよう、抽選された5問すべてを開始前に取得する。取得済み問題が壊れていた場合は挑戦を開始せず、同じ`runToken`をエラーとして処理する。別の5問へ黙って引き直さない。

### 14.3 記録取得失敗

ランキングの表示に失敗しても、ゲームは遊べるようにする。結果画面へ「ランキングを取得できませんでした」と再読込ボタンを表示する。

### 14.4 記録送信失敗

結果とローカル記録を維持し、再送できるようにする。送信失敗でホームへ強制移動しない。

### 14.5 予期しない例外

画面全体を覆う例外境界を用意する。次を表示する。

- 状況を初期化してホームへ戻る
- 直前の結果が保存済みなら結果を開く
- エラー識別番号
- 実験場へのリンク

例外の本文、環境変数、送信内容を画面へそのまま表示しない。

## 17. 自動検査

### 17.1 規則の単体検査

少なくとも次を固定試験にする。

- 回転量の正規化
- 左回転で`0`から`11`へ移る
- 反対側が6区画先になる
- 発射元より内側の遮断
- 中心通過後の遮断
- 同じ環の反対側の遮断
- 別の発光紋による遮断
- 停止中の発光紋による遮断
- 光どうしが互いを遮らない
- 同じ受信点への複数到達
- 必須受信点の全網羅
- 余分な光を許可
- 環選択が手数へ入らない
- 回転と切替が1手になる
- 入力直後の成功判定
- 状態符号化の無衝突
- 操作履歴の再生結果一致

### 17.2 探索と生成の検査

- 既知問題の最短手数
- 解なし問題を解ありとしない
- 同じシードで同じJSON
- 別シードで同じIDを作らない
- 初期状態が完成していない
- 難度範囲を外れた問題を採用しない
- 必要な発光切替を満たす
- 回転・反転重複を除外
- 同じ問題IDの内容変更を検知
- 問題チェックサム
- 問題庫チェックサム
- 抽選券チェックサム
- 壊れたJSONの拒否
- 公開用問題庫が初級30問・中級30問・上級30問の合計90問
- 90問が全件検証済み
- 抽選券が900件
- 各問題の抽選券内出現回数が仕様どおり
- 10万回抽選で難度構成、重複、出現率、校正値分布が基準内

### 17.3 画面検査

Playwrightで、次をChromiumとWebKitの両方で行う。

## 19. GitHub Actionsと公開

### 19.1 PR検査

PRでは、次を1つの検査系列として実行する。

```bash
npm ci
npm run typecheck
npm run lint
npm run test
npm run puzzles:test
npm run build
npm run test:e2e
```

同じビルドを複数のWorkflowで繰り返さない。

問題JSONまたは問題庫JSONだけのPRでは、画面E2Eを省略できる別経路を作ってよい。ただし、問題形式、全解法、問題庫、抽選券、抽選分布、ビルドの検査は省略しない。

### 19.2 main公開

`main`へのマージ後だけGitHub Pagesへ公開する。

- PRごとのプレビュー公開は初期実装では行わない
- 同じコミットを二重公開しない
- 同時公開は新しい実行を優先
- 公開物へコミットSHAを埋める
- 公開後にトップ、ゲーム開始、結果、404の簡易確認を行う
- 手動再公開を用意する
- 定期実行は使わない

### 19.3 GitHub Actions利用量

無駄な実行を減らす。

- push前にChatGPT Work環境で全検査
- 失敗修正を小刻みに何度もpushしない
- 文書だけの変更で重いブラウザ検査を走らせない
- 問題生成を定期実行しない
- main公開以外の重複Deployを作らない
- 既存Workflowがある場合は新設前に統合可能か確認する

## 23. ChatGPT Workの作業手順

各PRで、次の順を守る。

1. 最新の`main`を取得する。
2. 計画書と直前PRの報告を読む。
3. 対象PRの範囲だけを作業一覧へ分解する。
4. 既存実装と設定を確認する。
5. 先に失敗するテストを追加する。
6. 最小の実装でテストを通す。
7. 画面を実際に開く。
8. WebKit相当を含む検査を行う。
9. 不要なコード、仮データ、デバッグ表示を削除する。
10. 権利境界の全文検索を行う。
11. 全検査をローカルで成功させる。
12. 変更を意味のある単位でコミットする。
13. PRを作成する。
14. Actionsが失敗した場合は原因を特定して修正する。
15. PR本文を実測結果で更新する。
16. マージせず、ユーザーへ報告する。

ChatGPT Workは、計画書にない機能を「便利そう」という理由で追加しない。別の問題を見つけた場合は、今回の完了に必要か判断し、必要でなければPR本文の別課題へ記録する。

## 25. 仕様変更の扱い

公開後に次を変える場合は、`rulesetVersion`を上げ、旧ランキングと分ける。

- 光を遮る部品
- 光の進行経路
- 反対側の計算
- 発光切替の単位
- 成功条件
- 手数の数え方
- 可動環の本数
- 区画数

次は、規則版を変えずに修正できる。

- 石の色
- ひびの数
- 文章の誤字
- ボタンの余白
- 読み上げ文
- 送信失敗文
- 性能改善
- 同じ論理状態を保つアニメーション

難度範囲や問題生成乱数を変える場合は、`generatorVersion`を上げる。

90問の構成、校正値、抽選券、抽選比率を変える場合は、`poolVersion`を上げ、旧ランキングと分ける。

一度公開した問題JSON、問題庫JSON、抽選券は、誤字のように見える場合でも上書きしない。新しい問題IDまたは新しい`poolVersion`で差し替える。
